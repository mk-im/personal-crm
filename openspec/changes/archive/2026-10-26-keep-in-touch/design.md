# Design

## Context

См. proposal.md — Why. Сейчас у контакта нет частоты. Заметки уже есть, у них есть `created_at`. Список на главной: заголовок, поиск, затем все контакты. Данные только с сервера, Drizzle, Postgres.

## Goals / Non-Goals

**Goals:**

- Хранить частоту так, чтобы срок можно было посчитать без отдельного флага «просрочен».
- Не сбрасывать срок, если человек правил имя или телефон, а частоту не менял.
- Миграция только добавляет поля: текущие контакты без частоты, блок пустой.

**Non-Goals:**

- Новая таблица, очередь, крон, уведомления.
- Кэш просрочки в базе.

## Decisions

1. **Два поля у контакта, не отдельная таблица.** `keep_in_touch_frequency` (`weekly` / `monthly` / `quarterly` / `yearly` или пусто) и `keep_in_touch_set_at` (время, когда непустую частоту записали). Альтернатива — таблица истории: лишняя сложность для одной даты.

2. **Дата общения не хранится отдельно.** Если есть заметки — берём самую новую `notes.created_at`. Если нет — `keep_in_touch_set_at`. Альтернатива — поле `last_contacted_at`: его легко забыть обновить вместе с заметкой.

3. **`keep_in_touch_set_at` обновлять только когда меняется сама частота.** Сохранение остальных полей срок не двигает. Очистили частоту — оба поля пустые.

4. **Просрочку считать в запросе.** Сравнение «сейчас минус дата общения» с 7 / 30 / 90 / 365 днями, сортировка по величине просрочки, лимит 5. Альтернатива — ночное задание: для личного списка из тысяч контактов не нужно и устареет.

5. **Блок на главной между поиском и списком.** Поиск с `q` — блок не рендерить. Пустой результат — блока нет.

6. **Подписи в интерфейсе.** «Раз в неделю» и т.д. В базе — английские значения. Просрочка: «на N день/дня/дней», как счётчик контактов.

## Risks / Trade-offs

- [В блоке только пять человек, остальные просроченные не видны] → так решено; «показать ещё» не делаем.
- [Смена частоты без заметок заново запускает срок] → так решено; правка других полей срок не трогает.
- [Старые контакты сразу не попадут в блок] → частота пустая, пока человек сам её не задаст.

## Migration Plan

1. Миграция добавляет два nullable-поля. Уже лежащие строки не меняет.
2. Выкатка как обычно: PR → merge в `main` → миграции → новый образ.
3. Откат образа: старый код поля игнорирует. Схему назад — только вручную, если попросите.
