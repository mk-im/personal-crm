# Личная CRM

Список людей, которых знаете лично: кто это, откуда знакомы, телефон, почта и о чём договорились. К карточке можно дописать заметку после разговора.

Живое приложение: [app.crmc.space](https://app.crmc.space). Лендинг: [crmc.space](https://crmc.space).

## Как запустить

1. Запустите Docker Desktop.
2. В папке проекта выполните `docker compose up -d` — поднимутся PostgreSQL и почтовая заглушка Mailpit.
3. `pnpm install`
4. `pnpm db:migrate`
5. `pnpm db:seed` — добавит 1000 тестовых контактов владельцу из `OWNER_EMAIL`, если у него ещё нет контактов.
6. `pnpm dev` и откройте http://localhost:3000

Настройки лежат в `.env` (образец — `.env.example`): строка подключения к базе, адрес приложения и секрет входа, почта владельца, параметры SMTP и адрес отправителя.

## Вход

Пароля нет. На странице входа вы пишете почту и получаете письмо со ссылкой; ссылка живёт 15 минут и открывается один раз. Первый переход по ссылке создаёт аккаунт. Сессия живёт 30 дней с последнего захода; «Выйти» в шапке завершает сессию только на этом устройстве. Каждый видит только свои контакты, заметки и группы.

Локально письма не уходят в интернет: их принимает Mailpit, страница заглушки — http://localhost:8025. На сервере письма отправляет SMTP Resend.

## Как выкатывается на сервер

Слияние в ветку `main` собирает образ и выкатывает его только на тестовый стенд. Прод при этом не меняется.

На прод выкатываете вы сами, кнопкой.

1. Откройте репозиторий на GitHub, вкладка Actions.
2. Слева выберите **Deploy prod**.
3. Справа **Run workflow**.
4. Поле SHA оставьте пустым, галочку отката не ставьте, и запустите.

Пустое поле берёт версию последней зелёной выкатки на тест-стенд. Свой SHA в поле — запасной путь: эта версия тоже должна была успешно доехать до тест-стенда, иначе запуск остановится. Какой SHA уехал на прод, написано внизу зелёного запуска, в блоке Summary: строка `SHA`.

Перед сменой прода скрипт сохраняет копию базы. Имя файла начинается с `deploy_`, дальше версия, которая работала до этой выкатки, потом дата и время по всемирным часам. Файл лежит в `/home/crm/personal-crm/backups`. В логе есть строка `Backup written` и путь к файлу. Если копию сохранить не удалось или миграции не прошли, работающее приложение не меняется. Если проверка `/health` не прошла, выкатка останавливается с ошибкой и сама назад не откатывается.

Каждую ночь в 03:00 по Москве скрипт снимает ещё одну копию прода. Такие файлы начинаются с `daily_`. Копий перед выкаткой и ночных хранится по 7 последних. Файлы, которые уже лежат в папке и не начинаются с `deploy_` или `daily_`, скрипт не удаляет.

После удачной выкатки на прод старые образы чистятся. В GitHub остаются 10 последних сборок. На сервере удаляются образы старше двух недель, кроме двух последних версий прода и той, что сейчас на тест-стенде.

Две выкатки на одно и то же окружение одновременно не запускаются: вторая ждёт, пока закончится первая. Прод и тест-стенд друг друга не ждут.

## Как откатить прод

1. Actions → **Deploy prod** → **Run workflow**.
2. Поставьте галочку «Откатить прод на предыдущую версию». Поле SHA при этом не смотрится.
3. Запустите.

Сервер помнит версию, которая работала до текущей. Откат ставит её и не проверяет, была ли она на тест-стенде. Какой SHA встал, снова в Summary. Сама выкатка назад не откатывается: если проверка не прошла, напишите мне, кнопку нажимаете вы.

Кнопка отката начинает работать после первой выкатки на прод этим способом: именно тогда сервер запоминает предыдущую версию. Пока такой выкатки не было, запуск с галочкой остановится и напишет, что помнить ещё нечего.

## Как читать логи

Логи приложения на сервере пишутся в журнал системы. После выкатки, отката и пересоздания контейнера старые строки остаются. Журнал сам удаляет старые строки, когда место заканчивается, поэтому диск сервера не забивается.

Последние строки прода:

```
ssh crm "sudo journalctl --no-pager -n 100 CONTAINER_NAME=prod-app-1"
```

Последние строки тест-стенда:

```
ssh crm "sudo journalctl --no-pager -n 100 CONTAINER_NAME=staging-app-1"
```

Чтобы новые строки появлялись сразу, добавьте `-f` перед `CONTAINER_NAME`.

## Тестовый стенд

Адрес: [test-app.crmc.space](https://test-app.crmc.space). Браузер сначала спросит пароль стенда, потом откроется вход в приложение. Имя пользователя — `staging`. Пароль лежит только на сервере. Посмотреть его можно так:

```
ssh crm "sudo cat /home/crm/personal-crm-staging/basic-auth.password"
```

У стенда своя база и свой файл настроек `/home/crm/personal-crm-staging/.env`. Приложение слушает только `127.0.0.1:3001`, прод по-прежнему `127.0.0.1:3000`. Память контейнеров ограничена: стенд — 256 МБ на приложение и 128 МБ на базу, прод — 512 МБ и 256 МБ.

База стенда — копия прода на момент копирования. Выкатка стенда эту копию не перезаписывает и бэкап не снимает. Если базу стенда нужно заменить свежей копией прода, на сервере выполните:

```
sudo /home/crm/personal-crm/deploy/refresh-staging-db.sh
```

Скрипт покажет, какую базу стенда заменит, и будет ждать слово `yes`. Прод он только читает.

Письмо для входа ведёт на адрес того окружения, где вы запросили вход. Для этого в `.env` стенда строка `BETTER_AUTH_URL` должна быть `https://test-app.crmc.space`, а у прода — `https://app.crmc.space`. Кука входа ставится только на тот адрес, где вы вошли, без общего домена.

Чтобы письма со стенда уходили, в его `.env` нужна своя строка `MAIL_PASSWORD` — отдельный ключ почты, не из прода. Туда же добавьте `OWNER_EMAIL`, ту же почту владельца, что и на проде. Файл с сервера я не читаю и сюда не копирую.

Проверка после выкатки: откройте https://test-app.crmc.space, введите пароль стенда, запросите вход на свою почту. Ссылка в письме должна начинаться с `https://test-app.crmc.space`. В браузере у куки входа не должно быть домена `.crmc.space`. Прод в это же время открывается на https://app.crmc.space без пароля стенда.

## Как восстановить базу

Восстановление запускаете вы на сервере. Версия приложения при этом не меняется.

1. Выберите файл в `/home/crm/personal-crm/backups`. Новые файлы начинаются с `deploy_` или `daily_`, дальше идёт версия, которая работала, когда снимали эту копию.
2. На сервере выполните:

```
/home/crm/personal-crm/deploy/restore.sh /home/crm/personal-crm/backups/ИМЯ_ФАЙЛА.dump
```

3. Скрипт покажет файл и имя базы, которую заменит, и будет ждать слово `yes`.
4. Затем сохранит копию базы, как она есть сейчас, остановит приложение, удалит базу, создаст пустую и загрузит выбранный файл.
5. После этого снова запустит ту же версию приложения.

Если выбранный файл не читается как копия базы, приложение включится обратно, база останется как была. Если загрузка оборвётся после удаления базы, приложение останется выключенным. Копия, снятая перед восстановлением, лежит в той же папке `backups`.
